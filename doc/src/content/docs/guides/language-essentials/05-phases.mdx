Fixen programs enjoy **compositionality**: given two disjoint programs (sharing no relations), their union is a valid program whose evaluation is the union of the individual results. But what if you want to compose programs that **share** relations? For example, in static analysis, you might want to combine an interval analysis and a parity analysis, allowing them to exchange information during computation. A naive union of their rules fails because over-approximated facts subsume refined ones.

**Phases of execution** solve this by stratifying the program state into multiple fact databases, cycling through them as rules execute. This enables post-composition of rule sets and the modular composition of non-disjoint programs.

## Motivating Example: Composing Analyses

To motivate phases, consider building a static analyzer for a simple imperative language. Programs in this language have variable declarations, assignments, conditional branches, and sequence points. An example program is as follows (taken from [^1]):

```ansi frame="code" title="example.imp"
v [34m<-[0m [33m1[0m
[35mwhile[0m v [34m<=[0m [33m9[0m [35mdo[0m
    v [34m<-[0m v [34m+[0m [33m2[0m
[35mdone[0m
[35mif[0m v [34m=[0m [33m11[0m [35mthen[0m
    v [34m<-[0m [33m0[0m
[35mfi[0m
```

Running this program shows us that `v` is equal to `0` at the end of the program. Let us statically determine that this is the case.

First, we lower this program as an intermediate representation via a de-sugaring to basic statements in an assembly-like language:

```ansi frame="code" title="example.imp-ir"
  [36m0[0m: [35mvar[0m v
  [36m1[0m: v [34m<-[0m [33m1[0m
  [36m2[0m: [35mbranch[0m v [34m<=[0m [33m9[0m, [36m3[0m, [36m5[0m
  [36m3[0m: v [34m<-[0m v [34m+[0m [33m2[0m
  [36m4[0m: [35mjump[0m [36m2[0m
  [36m5[0m: [35mbranch[0m v [34m=[0m [33m11[0m, [36m6, [36m101[0m
  [36m6[0m: v [34m<-[0m [33m0[0m
[36m101[0m: [35mEND[0m
```

This allows us to easily represent the program using Fixen facts. The relation declarations are as follows:

```ansi frame='code' title="Relations for representing imperative programs"
[31mrel[0m [32mVar[0m: [33mLabel[0m, [33mString[0m
[31mrel[0m [32mAssign[0m: [33mLabel[0m, [33mString[0m, [33mExpr[0m
[31mrel[0m [32mBranch[0m: [33mLabel[0m, [33mExpr[0m, [33mLabel[0m, [33mLabel[0m
[31mrel[0m [32mSeq[0m: [33mLabel[0m, [33mLabel[0m
```

- `Var l v` states that program point `l` declares variable `v`.
- `Assign l x e` states that program point `l` assigns expression `e` to variable `x`.
- `Branch l e t f` states that program point `l` branches on expression `e`, jumping to `t` (true) or `f` (false) (this language assumes the [law of the excluded middle](https://youtu.be/K2tUymm5o4M?si=ffKdsN-nG1UpaiGb&t=149)).
- `Seq l l'` states that program point `l` is followed by `l'`.

For instance, the example program `example.imp-ir` is represented using the following Fixen facts:

```ansi frame='code' title="Facts for representing example.imp-ir"

[32mSeq[0m [34m0[0m [34m1[0m
```

### Interval Analysis

An **interval analysis** ascribes a range of possible values to each variable at each program point. Ideally, we should conclude that `v` belongs to the interval <Math formula="[0, 0]" /> at the end of the program.

Intervals assemble into a lattice, ordered by inclusion, i.e., <Math formula="[a, b] \sqsubseteq [c, d]" /> whenever <Math formula="a \geq c" /> and <Math formula="b \leq d" />. Interval joins and meets follow immediately from this order. Presume that we define the `Interval` data type (and associated order, join and meet functions) in Haskell (we show this later).

Then, we track program states with a relation:

```ansi frame="code" title="Lattice and relation for interval analysis"
[31mlat[0m [33mStateI[0m [31mwhere[0m
  [31mtype[0m = [33mHashMap String Interval[0m
  [31mleq[0m  = [35mstateILeq[0m
  [31mjoin[0m = [35mjoinI[0m
  [31mmeet[0m = [35mmeetI[0m

[31mrel[0m [32mStateBeforeI[0m: [33mLabel[0m, [33mStateI[0m
```
`StateI` is a **map lattice**, ordered by inclusion of map keys and the interval order on map values. The `StateBeforeI` relation maps each program label to a `StateI`. Essentially, at every program point, we track the intervals assigned to each variable that exists within the program.

The analysis rules initialize states and propagate them through assignments and branches:

```ansi frame="code" title="Interval analysis rules"

[31mrule[0m [33massignInitI[0m: [32mAssign[0m l _ _   [31m|-[0m [32mStateBeforeI[0m [33mHashMap[0m.[35mempty[0m 
[31mrule[0m [33mbranchInitI[0m: [32mBranch[0m l _ _ _ [31m|-[0m [32mStateBeforeI[0m [33mHashMap[0m.[35mempty[0m 
[31mrule[0m [33mvarInitI[0m:    [32mVar[0m l _        [31m|-[0m [32mStateBeforeI[0m [33mHashMap[0m.[35mempty[0m 

[31mrule[0m [33massignStepI[0m: [32mAssign[0m l x e, [32mSeq[0m l l', [32mStateBeforeI[0m l st
                  [31m|-[0m [32mStateBeforeI[0m l' ([33mHashMap[0m.[35minsert[0m x ([35mevalI[0m e st) st)

[31mrule[0m [33mbranchTrueI[0m: [32mBranch[0m l e t _, [32mStateBeforeI[0m l st,
                  [31mif[0m [33mBTrue[0m `[35mleq[0m` ([35mevalCondI[0m e st)
                  [31m|-[0m [32mStateBeforeI[0m t ([35mrefineTI[0m e st)

[31mrule[0m [33mbranchFalseI[0m: [32mBranch[0m l e _ f, [32mStateBeforeI[0m l st,
                  [31mif[0m [33mBFalse[0m `[35mleq[0m` ([35mevalCondI[0m e st)
                  [31m|-[0m [32mStateBeforeI[0m t ([35mrefineFI[0m e st)
```

The transfer functions (`assignStepI`, `branchTrueI`, `branchFalseI`) propagate states forward. The `evalI`, `evalCondI`, `refineTI`, and `refineFI` functions are defined in Haskell and evaluate expressions, check conditions, and refine intervals.

### Parity Analysis

A **parity analysis** determines whether each variable is even, odd, or unknown. It follows the same structure as the interval analysis but uses a different domain:

```txt
lat StateP where
  type = HashMap String Parity
  leq = statePLeq
  join = joinP
  meet = meetP
  bot = HashMap.empty

rel StateBeforeP: Label, StateP
```

The rules are analogous---initialization rules for `Var`, `Assign`, and `Branch`, followed by transfer functions that propagate parity information through the program.

### The Reduced Product Problem

Neither analysis alone is precise enough to prove that variable `v` equals `0` at the end of this program:

```txt
v <- 1
while v <= 9 do
    v <- v + 2
done
if v = 11 then
    v <- 0
fi
```

The interval analysis concludes `v in [0, 10]` at the end. The parity analysis concludes `v` is odd. Individually, neither is sufficient. But together --- via their **reduced product** --- we can prove `v = 0`: at the `if` statement, the interval `v in [10, 11]` combined with parity `v` is odd refines the interval to `v in [11, 11]`, which forces the true branch and yields `v = 0`.

A naive attempt composes the analyses by simply including both and adding exchange rules:

```txt
include "Parity"
include "Interval"

rule reducedExchangeI:
  StateBeforeP l st, StateBeforeI l st'
  -----------------------------------------------------
  |- StateBeforeI l (reduceInterval st st')
```

This rule refines interval bounds using parity information. Unfortunately, it is **completely inert**. Even if it derives the tighter interval `[11, 11]`, the over-approximated `[10, 11]` from the interval analysis rules strictly subsumes it. The solver drops the refined fact as redundant work.

The problem: both the over-approximated and refined facts coexist in the same database, and subsumption prevents the refinement from propagating.

## Phases of Execution

Phases solve this by **stratifying** the fact database into multiple independent databases. Facts in different databases do not subsume each other, so refined and unrefined facts can coexist without interference.

### Phase Declarations

Phases are declared with the `phases` keyword:

```txt
phases: [
  *,
  { reducedExchangeP, reducedExchangeI }
]
```

This declares a 2-phase program:
- **Phase 0** (`*`): all rules not explicitly listed — the transfer functions from the interval and parity analyses.
- **Phase 1**: the exchange rules that refine intervals using parity.

### How Phases Work

A phase declaration with `N` phases stratifies the execution state into `N` distinct fact databases, <Math formula="S_0, S_1, \ldots, S_{N-1}" />. Execution cycles modulo `N`:

- Rules in **phase i** draw their premises from database $S_i$.
- Their conclusions are inserted into database $S_{(i+1) \bmod N}$.

For our 2-phase program:

```
Phase 0 Rules (analyses)  ->  S1  ->  Phase 1 Rules (exchange)  ->  S0  ->  (repeat)
```

Phase 0 rules (the interval and parity transfer functions) draw from $S_0$ and stream their unrefined conclusions into $S_1$. Phase 1 rules (the exchange rules) consume these unrefined states from $S_1$, apply cross-domain refinements, and route the tighter facts back into $S_0$. Wider unrefined facts and narrower refined facts never coexist within the same database.

The complete program looks like this:

```txt
include "Parity"
include "Interval"

rule reducedExchangeP:
  StateBeforeP l st
  -------------------------
  |- StateBeforeP l st

rule reducedExchangeI:
  StateBeforeP l st, StateBeforeI l st'
  -----------------------------------------------------
  |- StateBeforeI l (reduceInterval st st')

phases: [
  *,
  { reducedExchangeP, reducedExchangeI }
]
```

The identity rule `reducedExchangeP` forwards parity facts intact from $S_1$ back to $S_0$, since parity state remains invariant across phase 1. The exchange rule `reducedExchangeI` consumes both parity and interval states from $S_1$, refines the interval using parity information, and writes the tightened interval back to $S_0$.

In subsequent iterations, phase 0 rules now use the refined intervals, producing tighter results that flow into $S_1$ again, where phase 1 rules can further refine. This cycle continues until a fixed point is reached.

### The Wildcard

The `*` wildcard in a phase declaration captures all rules not explicitly assigned to earlier phases. It is typically used for the "main" rules of a program (e.g., analysis transfer functions), while explicitly listed rules handle composition, refinement, or exchange logic.

```txt
phases: [
  *,                          -- transfer functions (inherited from includes)
  { exchangeRule }            -- exchange/refinement rules
]
```

### More Than Two Phases

Phases are not limited to two. You can declare any number of phases:

```txt
phases: [
  { initRules },              -- phase 0: initialization
  { transferRules },           -- phase 1: analysis transfers
  { widenRules }               -- phase 2: widening for convergence
]
```

With three phases, the cycle is: phase 0 -> $S_1$ -> phase 1 -> $S_2$ -> phase 2 -> $S_0$ -> (repeat). This allows more complex compositions, such as applying widening after the reduced exchange to guarantee convergence in infinite-height domains.

## Key Properties

- **Monotonicity is preserved**: the overall fixed-point computation remains monotone despite the multi-phase architecture.
- **State stratification**: facts in different databases are independent, preventing subsumption between refined and unrefined facts.
- **Modular composition**: individual analyses or rule sets can be developed independently and composed via phases.

## Summary

- **Phases** stratify the fact database into `N` independent databases, cycling through them during execution.
- Rules in phase `i` read from $S_i$ and write to $S_{(i+1) \bmod N}$.
- The `*` wildcard captures all unassigned rules.
- Phases enable **post-composition** of rule sets, supporting the modular composition of non-disjoint programs.
- This is essential for patterns like the **reduced product** of abstract interpretations, where cross-domain refinement must bypass subsumption.
