Fixen programs enjoy **compositionality**: given two disjoint programs (sharing no relations), their union is a valid program whose evaluation is the union of the individual results. But what if you want to compose programs that **share** relations? For example, you might want to combine an interval analysis and a parity analysis, allowing them to exchange information during computation. A naive union of their rules fails because over-approximated facts subsume refined ones.

**Phases of execution** solve this by stratifying the program state into multiple fact databases, cycling through them as rules execute. This enables post-composition of rule sets and the modular composition of non-disjoint programs.

## Motivating Example: Composing Analyses

To motivate phases, consider building a static analyzer for a simple imperative language. Programs in this language have variable declarations, assignments, conditional branches, and sequence points. We represent such programs as Fixen facts:

```txt
rel Var: Label, String
rel Assign: Label, String, Expr
rel Branch: Label, Expr, Label, Label
rel Seq: Label, Label
```

* `Var l v` states that program point `l` declares variable `v`.
* `Assign l x e` states that program point `l` assigns expression `e` to variable `x`.
* `Branch l e t f` states that program point `l` branches on expression `e`, jumping to `t` (true) or `f` (false).
* `Seq l l'` states that program point `l` is followed by `l'`.

### Interval Analysis

An **interval analysis** ascribes a range of possible values to each variable at each program point. We represent intervals using a lattice, and track program states with a relation:

```txt
lat StateI where
  type = HashMap String Interval
  leq = stateILeq
  join = joinI
  meet = meetI
  bot = HashMap.empty

rel StateBeforeI: Label, StateI
```

`StateBeforeI` maps each program label to a state (a HashMap from variable names to intervals). The analysis rules initialize states and propagate them through assignments and branches:

```txt
rule assignInitI: Assign l _ _ |- StateBeforeI l HashMap.empty
rule branchInitI: Branch l _ _ _ |- StateBeforeI l HashMap.empty
rule varInitI: Var l _ |- StateBeforeI l HashMap.empty

rule assignStepI:
  Assign l x e, Seq l l', StateBeforeI l st
  ---------------------------------------------------------------------
  |- StateBeforeI l' (HashMap.insert x (evalI e st) st)

rule branchTrueI:
  Branch l e t _, StateBeforeI l st, if BTrue `leq` (evalCondI e st)
  ----------------------------------------------------------------------------------------------
  |- StateBeforeI t (refineTI e st)

rule branchFalseI:
  Branch l e _ f, StateBeforeI l st, if BFalse `leq` (evalCondI e st)
  -----------------------------------------------------------------------------------------------
  |- StateBeforeI f (refineFI e st)
```

The transfer functions (`assignStepI`, `branchTrueI`, `branchFalseI`) propagate states forward. The `evalI`, `evalCondI`, `refineTI`, and `refineFI` functions are defined in Haskell and evaluate expressions, check conditions, and refine intervals.

### Parity Analysis

A **parity analysis** determines whether each variable is even, odd, or unknown. It follows the same structure as the interval analysis but uses a different domain:

```txt
lat StateP where
  type = HashMap String Parity
  leq = statePLeq
  join = joinP
  meet = meetP
  bot = HashMap.empty

rel StateBeforeP: Label, StateP
```

The rules are analogous---initialization rules for `Var`, `Assign`, and `Branch`, followed by transfer functions that propagate parity information through the program.

### The Reduced Product Problem

Neither analysis alone is precise enough to prove that variable `v` equals `0` at the end of this program:

```txt
v <- 1
while v <= 9 do
    v <- v + 2
done
if v = 11 then
    v <- 0
fi
```

The interval analysis concludes `v in [0, 10]` at the end. The parity analysis concludes `v` is odd. Individually, neither is sufficient. But together --- via their **reduced product** --- we can prove `v = 0`: at the `if` statement, the interval `v in [10, 11]` combined with parity `v` is odd refines the interval to `v in [11, 11]`, which forces the true branch and yields `v = 0`.

A naive attempt composes the analyses by simply including both and adding exchange rules:

```txt
include "Parity"
include "Interval"

rule reducedExchangeI:
  StateBeforeP l st, StateBeforeI l st'
  -----------------------------------------------------
  |- StateBeforeI l (reduceInterval st st')
```

This rule refines interval bounds using parity information. Unfortunately, it is **completely inert**. Even if it derives the tighter interval `[11, 11]`, the over-approximated `[10, 11]` from the interval analysis rules strictly subsumes it. The solver drops the refined fact as redundant work.

The problem: both the over-approximated and refined facts coexist in the same database, and subsumption prevents the refinement from propagating.

## Phases of Execution

Phases solve this by **stratifying** the fact database into multiple independent databases. Facts in different databases do not subsume each other, so refined and unrefined facts can coexist without interference.

### Phase Declarations

Phases are declared with the `phases` keyword:

```txt
phases: [
  *,
  { reducedExchangeP, reducedExchangeI }
]
```

This declares a 2-phase program:

* **Phase 0** (`*`): all rules not explicitly listed — the transfer functions from the interval and parity analyses.
* **Phase 1**: the exchange rules that refine intervals using parity.
