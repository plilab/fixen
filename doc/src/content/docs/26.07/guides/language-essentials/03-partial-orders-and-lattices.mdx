By default, Fixen treats all types as **discrete** — two facts match only if their values are exactly equal. For many problems, this is sufficient. But for problems like shortest paths or abstract interpretation, you need the solver to understand that some facts are "better" than others and can subsume weaker ones. This is where partial orders and lattices come in.

## Lattice Declarations

A lattice declaration tells Fixen that a type has a partial order and a join operation. Facts whose values are drawn from a lattice type are automatically merged when they share the same key.

```fixen
lat Dist where
  type = Natural
  leq = (>=)
  join = min
```

This declares `Dist` as a lattice based on Haskell's `Natural` type. The `leq` field specifies the partial order: `a >= b` means that smaller distances are "greater" (better). The `join` field specifies how to merge two values: `min` keeps the smaller distance.

When the solver derives `DistTo "Paris" 5` and later `DistTo "Paris" 3`, it merges them using `min 5 3 = 3`, retaining only the better fact.

### Lattice Fields

A `lat` declaration has four required fields:

| Field | Purpose | Example |
|-------|---------|---------|
| `type` | The underlying Haskell type | `Natural` |
| `leq` | The partial order (≤) | `(>=)` |
| `join` | The join operation (least upper bound) | `min` |
| `meet` | The meet operation (greatest lower bound) | `max` |

The `meet` field is used for **map-entry unification**: when two premises share a variable and both reference lattice-valued arguments, the solver computes their meet to find a common instantiation. See [Map-Entry Unification](#map-entry-unification) for details.

## Partial Order Declarations

A partial order declaration is like a lattice, but without the join operation. Facts are still compared and subsumed, but they are never automatically merged.

```fixen
partial ord Dist where
  type = Natural
  leq = (>=)
  mlbs = distMlbs
```

The key difference from a lattice: when two facts share a key but have incomparable values, both are retained. This is essential for **Pareto-optimal** computations like multi-objective shortest paths, where a path that is shorter but slower should not be discarded in favor of a path that is faster but longer.

### Partial Order Fields

A `partial ord` declaration has three required fields:

| Field | Purpose | Example |
|-------|---------|---------|
| `type` | The underlying Haskell type | `Natural` |
| `leq` | The partial order (≤) | `(>=)` |
| `mlbs` | Maximal lower bounds function | `distMlbs` |

The `mlbs` (maximal lower bounds) function computes the list of maximal elements that are lower bounds of two inputs. This is used for map-entry unification, analogous to `meet` in lattices. For discrete types, `mlbs` defaults to returning a singleton list for equal values and an empty list otherwise.

## Subsumption

Partial orders and lattices define **fact subsumption**. A fact `f1` subsumes a fact `f2` if `f2 ⊑ f1` — that is, `f1` is "greater than or equal to" `f2` under the declared order.

Subsumption works at the level of **tuples of arguments**. For a relation `Rel A B C`, the order is defined structurally:

```
Rel a1 b1 c1 ⊑ Rel a2 b2 c2
  iff a1 ⊑ₐ a2 ∧ b1 ⊑ᵦ b2 ∧ c1 ⊑𝒸 c2
```

Each sort contributes its own partial order to the product order. Sorts without an explicit ordering declaration are treated as **discrete** (equality only).

In the graph distance example, `Dist` is ordered by `>=` (smaller is better). Therefore:

```
DistTo "Paris" 3 ⊑ DistTo "Paris" 5
```

because `3 >= 5` is true under the declared order. The solver retains only `DistTo "Paris" 3` and discards the subsumed fact.

## Map-Entry Unification

When two premises in a rule share a variable and both reference lattice-valued (or partially ordered) arguments, the solver must find a common instantiation. This is called **map-entry unification**.

For lattice domains, this corresponds to the **meet** (greatest lower bound) operation. For general partial orders, the solver uses the `mlbs` function to compute a list of maximal lower bounds, non-deterministically instantiating the shared variable with each candidate.

Consider this rule:

```fixen
rule transitive: R x y, R y z |- R x z
lat Nat where
  type = Natural
  leq = (<=)
  join = max
  meet = min
```

If the database contains `R 5 2` and `R 4 7`, a naive solver would fail to fire this rule because `2 ≠ 4`. But under the lattice order `≤`, the fact `R 4 7` subsumes `R 2 7` (since `2 ≤ 4`). The solver computes `meet 2 4 = min 2 4 = 2`, instantiating the shared variable as `2`, and derives `R 5 7`.

## Complete Example: Dijkstra's Algorithm

The following is a complete, self-contained Fixen program implementing Dijkstra's shortest-path algorithm. It demonstrates how relations, rules, and a lattice declaration work together.

````fixen
module Demos.ShortestPath where

import Numeric.Natural

```hs
type Vertex = String
````

lat Dist where
type = Natural
leq = (>=)
join = min
meet = max

rel DistTo: Vertex, Dist
rel Edge: Vertex, Vertex, Dist

rule edgeToPath: Edge u v |- DistTo u 0
rule addDist: DistTo u d, Edge u v d' |- DistTo v (d + d')

````

To run this program, provide initial edge facts to `solve`:

```haskell
import Demos.ShortestPath

main :: IO ()
main = do
  let edges = [ Edge "A" "B" 1
              , Edge "B" "C" 2
              , Edge "A" "C" 10
              , Edge "C" "D" 1
              ]
      db = solve edges
  -- db now contains the shortest distances from "A" to all reachable vertices
````

The `lat Dist` declaration is what makes this program terminate on cyclic graphs. Without it, the `addDist` rule would keep deriving longer and longer paths around cycles. With the lattice, `DistTo "C" 10` is subsumed by `DistTo "C" 3` (since `3 >= 10` is true under `>=`), and the solver retains only the shorter distance.

## Complete Example: Bi-Objective Shortest Paths

Now consider a variant where each edge has both a distance and a cost. We want to find all Pareto-optimal (distance, cost) pairs for each vertex — paths that are not dominated by any other path on both metrics.

````fixen
module Demos.Pareto where

import Numeric.Natural

```hs
type Vertex = String
````

partial ord Dist where
type = Natural
leq = (>=)
mlbs = distMlbs

rel DistTo: Vertex, Dist, Cost
rel Edge: Vertex, Vertex, Dist, Cost

rule edgeToPath: Edge u v d c |- DistTo u 0 0
rule addDist: DistTo u d c, Edge u v d' c' |- DistTo v (d + d') (c + c')

```

The key difference from Dijkstra's algorithm is the use of `partial ord` instead of `lat`. When the solver derives `DistTo "C" 3 10` and later `DistTo "C" 10 3`, these are **incomparable** under the partial order (neither `3 >= 10 ∧ 10 >= 3` nor `10 >= 3 ∧ 3 >= 10` holds). A lattice would merge them via `min`, producing `DistTo "C" 3 3` — a spurious path that doesn't exist in the graph. The partial order preserves both facts, maintaining the true Pareto frontier.

## Choosing Between Lattices and Partial Orders

The choice between `lat` and `partial ord` determines how the solver handles **incomparable** facts:

- **Lattices** — every pair of values has a join. When two facts share a key with different values, they are automatically merged via the join operation. This is appropriate when you want a single representative value per key (e.g., shortest distances, interval bounds).

- **Partial orders** — not every pair is comparable, and there is no automatic merge. Incomparable facts are retained as separate entries. This is appropriate when you need to preserve the full set of non-dominated values (e.g., Pareto frontiers in multi-objective optimization).

As a rule of thumb:
- Use `lat` when you have a single objective and want the solver to automatically merge competing facts.
- Use `partial ord` when you need to track multiple incomparable values per key.

## Summary

- **Lattices** (`lat`) define a partial order with a join operation. Facts sharing a key are automatically merged via join.
- **Partial orders** (`partial ord`) define a partial order without automatic merging. Incomparable facts are retained.
- **Subsumption** is defined by the product of partial orders over relation arguments.
- **Map-entry unification** uses `meet` (lattices) or `mlbs` (partial orders) to match variables across premises.
- Choose `lat` for single-objective problems; choose `partial ord` for Pareto-optimal or multi-objective problems.
```
